# 混合召回 RAG 知识库系统

> 向量语义召回 + BM25 关键词召回双路融合的检索系统，全链路离线。
> 每条召回结果强制携带 `citation`（条目 ID + 偏移量）与召回路径标记，
> **从机制上抑制编造，而不是靠 prompt 约束**。

| | |
|---|---|
| 后端 | FastAPI，**23 个模块 / 2,156 行 Python** |
| 向量模型 | `BAAI/bge-small-zh-v1.5`（本地部署，512 维） |
| 语音 | `faster-whisper`（本地部署，ASR） |
| 检索 | 向量语义 + BM25 双路，RRF / 加权归一化两种融合 |
| 中文分词 | CJK 单字 + 相邻双字 n-gram，**不引 jieba，零依赖** |
| 测试 | **82 例 pytest** |

## 一、为什么必须做混合召回

这个项目最初只有向量语义检索。实测中发现一个很具体的问题：

> **纯语义检索在专有名词和编号上会漏召回。**

比如查「工号 10086 的考勤记录」，向量模型会把「10086」当成普通数字，
语义上跟一串别的数字很接近，真正含这个工号的文档反而排不进候选池。

原因不难理解：embedding 是为**语义相似**优化的，而工号、订单号、人名这类 token
需要的恰恰是**精确匹配**，语义相似度在这里是噪声。

所以加了 BM25 一路。下面是**实测数据**（见第六节）：

| 方案 | MRR@5 | Hit@5 | Recall@10 | 命中时平均名次 |
|---|:---:|:---:|:---:|:---:|
| 纯向量语义 | 0.8418 | 0.8980 | 0.9286 | 4.77 |
| 纯 BM25 关键词 | 0.7560 | 1.0000 | 1.0000 | 1.49 |
| 混合 · RRF (k=60) | 0.7988 | 0.9541 | 0.9796 | 1.87 |
| **混合 · 加权 (α=0.5)** | **0.9154** | **1.0000** | **1.0000** | **1.18** |

**相对纯向量，加权融合的 MRR@5 提升 8.7%，命中时平均名次从 4.77 提到 1.18（约 4 倍）。**

## 二、三种融合策略

| 策略 | 实现 | 适用 |
|---|---|---|
| **RRF（倒数排名融合）** | `score = Σ 1/(k + rank_i)`，`k = 60` | 默认。**只用名次，免疫分数不可比问题** |
| **加权归一化融合** | min-max 归一化后按 `alpha` 加权 | 两路分数同量纲时，能利用分数强度信息 |

### 为什么默认用 RRF

不同检索器的分数**不可比**：cosine 相似度挤在 0.7~0.95 的窄区间，BM25 分数可能是 0~30 且无上界。
直接加权融合，权重没有物理意义，还得先做归一化。

RRF 只用名次，天然绕开量纲问题。代价是丢掉了分数里携带的置信度信息，
所以加权融合也一并保留，按需切换。

### 一个反直觉的实测结果：RRF 反而不如加权

上表里 **RRF（0.7988）居然低于纯向量（0.8418）**，跟"RRF 更稳"的直觉相反。

原因：RRF 丢弃了分数强度。而这次实验的 query 是从 chunk 原文里抽的句子，
**字面重合度极高，BM25 这一路本身就极准**（平均名次 1.49）。
RRF 把这条强信号稀释成了"第 1 名"，反而让向量的次优排序拖了后腿。

所以实际策略是**按 query 类型选融合**：

- 字面匹配为主的查询（查编号、查原文、查术语）→ **加权融合**，吃满 BM25 的精确性
- 语义改写多的查询（同义问法、口语化提问）→ **RRF**，避免 BM25 分数尺度干扰

这个结论是跑出来的，不是想出来的。

## 三、中文分词：为什么不引 jieba

```python
def tokenize(text):
    # 单字：过滤虚词（的了是在和与就都而…）
    # 双字：相邻 n-gram，且至少一个字为实义
```

三点考虑：

1. **零依赖**。jieba 要带词典，在离线部署场景里多一份负担。
2. **对未登录词天然友好**。工号、产品型号、人名这类词，词典里没有就是没有；
   n-gram 不看词典，切出来照样能命中。
3. **双字过滤虚词**是关键一步。只过滤单字虚词时，「的了吗呢」仍会切出
   `['的了','了吗','吗呢']` 这种噪声词，导致任何含「的」的中文文档都被误召回。
   所以双字要求**至少一个字为实义**，「目的」留下，「的了」丢掉。

### BM25 参数

`k1 = 1.5`（词频饱和，出现 10 次不该是 1 次的 10 倍价值）
`b = 0.75`（长度归一化，长文档天然词频高，要惩罚）
`idf = ln(1 + (N - df + 0.5) / (df + 0.5))`

## 四、Citation：把防编造做成机制，不是提示词

很多 RAG 系统的做法是「在 prompt 里写一句：请只根据给定内容回答」。
**prompt 约束在模型幻觉面前是靠不住的。**

这个项目的做法是在数据结构层强制：

```python
{
    "citation": {"entry_id": "...", "offset": 1234},   # 条目 + 偏移量
    "recall_path": "hybrid:vector+bm25",               # 召回路径标记
    ...
}
```

每条召回结果**必须**带 `citation` 和 `recall_path`，生成时只能引用带 citation 的片段。
这样「这句话是从哪来的」永远可查，不需要信任模型的自觉性。

切片策略：`300 字 / 50 字重叠`。

## 六、检索效果评测

脚本：`eval/bench_recall.py`，结果：`eval/recall_bench_result.json`

```
去重后文档 5 篇 -> 切分为 204 个 chunk（300 字 / 50 字重叠）
向量维度 = 512
构造查询 196 条（每个 chunk 一条，正例即该 chunk）
```

**方法说明（诚实交代）**：无标注语料，采用自监督构造——从每个 chunk 抽一个完整子句作为 query，
正例即该 chunk。这让 BM25 天然占优（字面重合度高），所以**这张表主要用来看
"混合相对单一路是否有增益"，不适合当作绝对检索能力的评测**。

更贴近真实的分层评测（人工标注 query、区分语义改写型与字面匹配型）是下一步。

## 八、已知局限（诚实写在这里）

1. **语料规模小**。31 条条目里大量重复导入，**去重后只有 5 篇文档**（约 5 万字），
   切出 204 个 chunk。混合召回的价值在大规模语料上才更明显。
2. **评测用自监督构造的 query**（从 chunk 抽子句，正例即自身），
   对 BM25 天然有利。**这张表只能证明"混合优于单一路"，不能当作绝对检索能力**。
   人工标注的分层评测是下一步。
3. **没有做 rerank**。融合结果直接进生成，没有 cross-encoder 二次精排。
   语料规模上去之后，rerank 是最该补的一环。
4. **没有接入向量数据库**。当前是内存索引（NumPy），
   万级以下够用；更大规模需要 FAISS / HNSW。
5. **融合权重 `alpha = 0.5` 是人工设定的**，没有用标注数据做过网格搜索。
6. **没有知识图谱的运行时检索**。代码里有 `knowledge_graph.py`
   （LLM 抽知识点 → 建节点 → 判定关系 → 建树），但当前没有接入检索链路。
